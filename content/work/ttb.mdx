<Section n="02" title="Context & problem">

ttb is a large Thai bank. I worked on Flutter apps under the bank's security rules — locked-down machines, restricted websites and installs, and checked network connections — and inside its process: specs in Jira, merge requests, code review and Jenkins pipelines.

Two everyday problems shaped my first projects. Developers relied on outside websites for routine utilities, which didn't fit bank policy and showed ads. And the Business Analysis team edited many versions of Excel files on Confluence, so data conflicted when people edited at once.

</Section>

<Section n="03" title="My role">

Software Engineer Tech Intern in the ttb spark Tech & Data Internship, on the Tablet Platform Digital Solution team. I built three tools and the release automation for the team's internal tools app, owned the Activity Log end to end — requirements, navigation, auth and features — and contributed features to the enterprise platform.

The Business Analysis team described problems in business terms, so I asked questions and confirmed my understanding with wireframes and flows before building, to avoid rework.

</Section>

<Section n="04" title="What I built">

### Internal developer tools

- **CSV↔JSON parser** with chunked processing and a progress bar.
- **Regex tester** with presets, flags and highlighting.
- **QR code generator** with validation.
- **A shared analytics component** that logs events through Firebase Analytics.
- **Release automation:** Fastlane + Melos with four lanes — analyze, unit test, version bump, and deploy to Firebase App Distribution.

### Activity Log for the Business Analysis team

- Central data on Cloud Firestore and Realtime Database.
- A data dictionary with full CRUD and a guard against duplicate fields.
- A version log that stores only changed rows. I agreed the Firestore data structure with the developer of another feature so history displays correctly.
- Single-device login tied to the device, with live session tracking.
- Cache-first data with a stale fallback, and the TTL controlled through Remote Config.
- Excel export, continuing work started by another intern.

### Enterprise platform team

An all-in-one platform for staff and branches. I joined while the team was moving from a monorepo to micro-frontends.

- Helped migrate code between releases.
- Studied Git submodules to bring team repositories together for testing.
- Real-time unread-message notifications with Cubit and WebSocket.
- An idle timeout that works across several browser tabs.

</Section>

<Section n="08" title="What I'd change">

- **Push back earlier, with evidence.** On the idle-timeout feature I proposed a different approach from the spec; the team chose to change the spec back to existing behaviour. Next time I'd bring a quick prototype and the trade-offs to the first discussion, so the decision is made before the work, not after.
- **Budget time for setup and onboarding.** Setting up a dev environment on locked-down bank machines (an Android emulator blocked by network certificate checks) and learning existing code mid-migration took longer than I planned. I'd now set up and read the codebase in week one, and ask the owners directly sooner.
- **Report progress and blockers daily.** Near the end I was juggling sprint tickets and a proof of concept; breaking work into small tracked pieces and flagging blockers early worked far better than waiting until near the deadline.

</Section>
