<Section n="02" title="Context & problem">

For the Project Management course, a 10-person team built a smart locker system. A user rents a locker for a set number of hours, pays, and opens or closes it from their phone. Admins manage the lockers, sizes and prices.

The team split the work into a user app, an admin app, a driver for the locker hardware and the backend. The backend sits in the middle: every app reads and writes through it, and it is the only part that tells a locker door to open.

</Section>

<Section n="03" title="My role">

Backend developer, one of two on the backend. I worked with the frontend developer to agree the API the apps would call.

My teammate set up the project skeleton, sign-up and login, connected the locker hardware, and added the overtime checkout, the payment-expiry job and the LINE end-time warnings. I built the rest of the domain on top of that, listed below.

</Section>

<Section n="04" title="What I built">

### Structure and data

- **Layered structure:** split the code into handlers, services and repositories, each behind an interface.
- **PostgreSQL schema:** the tables, foreign keys, data types and delete/update constraints in the Flyway migrations.
- **Resource endpoints:** create, read, update and delete for lockers, locker sizes, price settings, rentals and payments, plus user lookup — with responses that include the related locker, size and user details.

### Rentals and payments

- **Start a rental:** the locker must be available and the user must have no pending payment. The price is paid hours × the hourly rate for that locker size.
- **End a rental:** time used is rounded up to the hour. On time, the rental completes and the locker opens. Over time, the extra hours × the size's overtime rate become a pending PromptPay payment.
- **Overtime recalculation:** when the overtime is paid, the rental's total is recalculated and it completes.

### Access and hardware

- **JWT with roles:** middleware verifies the token and the role, wired into every route. Lockers, sizes, prices and users are admin-only.
- **Remote open and close:** a user can open or close only the locker they are renting. The command goes to the locker hardware through the device client my teammate wrote.

### Quality

- **Unit tests:** 30 tests over 7 services — auth, users, lockers, sizes, prices, rentals and payments — with mocked repositories.
- **Clearer errors:** ID validation on requests and user-facing error messages in Thai.

</Section>
