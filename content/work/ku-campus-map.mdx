<Section n="01" title="TL;DR" id="tldr">

- University maps are mostly flat images that are hard to read; I wanted to see if a 3D map could make finding your way around campus more engaging.
- Built a static 3D site from real OpenStreetMap data, with 38 places, Thai/English search and the campus shuttle routes.
- Made it work on phones: custom touch gestures, a code-split 3D chunk and render-on-demand.

</Section>

<Section n="02" title="Context & problem">

Most university campus maps are the old, static kind — a flat image or a PDF that's hard to read and harder to search. I was curious to try 3D, and thought a map you can rotate, tap and search would make exploring the campus more exciting for freshmen and visitors.

</Section>

<Section n="03" title="My role">

I worked alone, owning the product, the design direction, the data and the testing. Claude Code wrote the code in seven milestones — scaffold, styled scene, gestures, search and filters, shuttle, performance, deploy — committing after each one. I planned each milestone, wrote the briefs, reviewed every checkpoint with screenshots, and tested on my own iPhone between rounds.

The data I checked myself:

- Reviewed the landmark list: names in Thai and English, nicknames, and which places count as landmarks.
- Used only open-licensed photos (Wikimedia Commons) or my own.
- Replaced made-up stop names with neutral labels, and marked approximate stops as “Near …”.

The shuttle data comes from the official route maps and the 2026 schedule on vehicle.ku.ac.th. 32 of 39 OpenStreetMap stops matched an official stop; the approximate ones are labelled.

</Section>

<Section n="04" title="How I built it">

**Visual direction.** Clean, bright, low-poly isometric 3D with soft shadows and rounded floating cards, inspired by a logistics-dashboard reference and recoloured in KU green. The font is IBM Plex Sans Thai.

**A hybrid map.** Roads, building footprints and positions are real OpenStreetMap data. Featured landmarks get detailed low-poly models; everything else stays a plain block. Labels are capped at the default view so the map stays readable.

Problems I found by testing on a real phone, then fixed:

- Shuttle routes leaked onto public roads and broke into pieces. Fixed by constraining the trace to campus roads and adding a validator.
- The map looked blurry on an iPhone 13 because of a resolution cap. Fixed with adaptive resolution — full when still, lower while moving — and a `?debug=1` performance overlay.
- The bottom sheet fought with scrolling. Fixed with drag-from-anywhere and scroll hand-off.
- Link previews showed a logo. Fixed with a real map share image.

</Section>

<Section n="05" title="What it does">

- A 3D campus from OpenStreetMap buildings, roads, water and trees; 16 landmarks have hand-styled models.
- 38 places in 8 categories, each with Thai and English text, sources and photos.
- Search in Thai and English, including nicknames and shuttle stop codes, with category filter chips.
- A detail card on desktop and a three-position bottom sheet on mobile. Places are shareable by link (`?place=library`).
- The KU shuttle (รถตะลัย) overlay: lines 1, 3 and 5 with stops and service hours.
- Thai by default, English one tap away.

<Section n="06" title="Decisions & trade-offs">

<Decision
  title="Real map data, fetched once"
  why="OpenStreetMap geometry is pulled by a script at build time and stored as one compact TopoJSON file, so the app never calls a map API. Six GeoJSON files (~138 KB gzipped) became one ~77 KB file."
/>
<Decision
  title="Hand-written touch gestures"
  why="Pan with fling, pinch, two-finger rotate and tilt, double-tap zoom — written by hand to feel like Google Maps on phones, instead of relying on desktop-style orbit controls. Tested with Playwright driving real touch input, including WebKit for Safari."
/>
<Decision
  title="Shell first, 3D later"
  why="The UI shell (124 KB gzipped) paints first; three.js, the scene and the map data (360 KB) load as a separate chunk afterwards, behind a campus-shaped loading skeleton. Previously everything was one 545 KB bundle."
/>
<Decision
  title="Render on demand"
  why="The scene draws zero frames while the map is still, which saves battery on phones; shadows render only at rest, and resolution adapts on phones."
/>
<Decision
  title="Shuttle routes from official images"
  why="A Python tool traced KU's official shuttle route images onto campus roads, with a validator script that checks every route is one continuous loop."
/>

</Section>

<Section n="07" title="Architecture">

<KuCampusMapDiagram />

Build-time scripts turn OpenStreetMap data into trees, a campus fade mask and one TopoJSON file, and a Python tracer produces the shuttle routes. At runtime the React shell drives the lazily loaded 3D scene through a small map API.

</Section>

<Section n="09" title="What I'd change">

Total Blocking Time didn't improve (0.78 s → 1.20 s). Building the 3D scene is now split into shorter tasks, but the total work is the same and the CPU throttle still counts it. Next I'd:

- pre-build the scene geometry at build time or in a Web Worker
- show a poster image first, then cross-fade into 3D
- self-host a subset of the font
- add offline support for weak campus Wi-Fi

I'd also verify the approximate shuttle stops on campus.

</Section>
